# CERNAL — מדריך התחלה לחברי הצוות

<div dir="rtl">

המדריך הזה מיועד למי שאף פעם לא השתמש ב-Git, אף פעם לא פתח טרמינל, ובא לפרויקט מהצד הביולוגי.
אין כאן שום דבר שצריך לדעת מראש. עברו על השלבים לפי הסדר, והעתיקו־הדביקו את הפקודות כמו שהן.

כל הפקודות, הנתיבים ושמות הקבצים כתובים באנגלית ומופיעים בשורות נפרדות — זה נועד כדי שתוכלו לסמן, להעתיק ולהדביק בלי לשנות תו אחד.

---

## 1. מה זה הריפו הזה

**CERNAL הוא קומפיילר**: הוא מקבל חתימה טרנסקריפטומית (טבלת ביטוי גנים) ומוציא ממנה מעגל לוגי מ-RNA שמורכב על פלסמיד.
**הריפו הזה הוא השלד המשותף**: כל המחלקות, כל שמות הפונקציות, כל טיפוסי הנתונים וכל התיעוד כבר כתובים — 138 פונקציות ציבוריות, מתוכן 90 כבר עובדות ו-48 עדיין ריקות.
**התפקיד שלכם**: למלא את הפונקציות הריקות ששייכות לתחום שלכם — לא לכתוב מודול חדש מאפס.

### התמונה הגדולה

עד היום כל אחד ואחת מכם עבדו על הקוד שלהם בריפו נפרד. עכשיו הכל מתכנס לכאן. זה נראה כמו הפסד — בפועל זה רווח גדול, בגלל סיבה אחת:

> אם שני אנשים מחשבים את אותו גודל פיזיקלי בשתי דרכים שונות, שני המספרים נראים סבירים, אף אחד לא קורס, והדירוג הסופי של המעגלים פשוט יוצא **שגוי בשקט**.

בדיוק בשביל זה יש כאן פונקציות משותפות. אנרגיית קיפול מחושבת במקום אחד. חיפוש off-target מחושב מול אינדקס אחד. תוכן GC מחושב בפונקציה אחת. כשכולנו קוראים לאותו קוד, המספרים של כולנו ניתנים להשוואה — וזו כל המטרה של הפרויקט.

מה שזה אומר בפועל: **הרבה מהקוד שכתבתם תמחקו, ובמקומו תקראו לפונקציה שכבר קיימת בריפו.** זה לא ביזבוז — זה בדיוק העבודה. הקוד המדעי שלכם, ההחלטות והפרמטרים — אלה נשארים.

### הכלי שאיתו תעבדו

לכולם מותקן Claude Code. הוא קורא אוטומטית את הקובץ `CLAUDE.md` ואת התיקייה `.claude/` בפרויקט, כך שהוא כבר מכיר את כללי הבית של הריפו. תפתחו אותו **בתוך תיקיית הפרויקט** ותדברו איתו בשפה חופשית (עברית או אנגלית). הוא כותב את הקוד — אתם מחליטים מה נכון מדעית ובודקים.

## 2. התקנה (פעם אחת)

### שלב 0 — לא לשמור את הפרויקט ב-OneDrive. זה לא ניתן למשא ומתן.

OneDrive מסנכרן גם את הקבצים הפנימיים של Git (התיקייה המוסתרת `.git`), נועל אותם באמצע כתיבה ולפעמים מחזיר גרסאות ישנות — וכך הוא הורס את הריפו. **זה כבר קרה פעם אחת במחשב של עופר.**

לכן: הפרויקט יושב ב-`C:\dev\cernal_software`, לא ב-OneDrive, לא בשולחן העבודה שמסונכרן, ולא ב-Google Drive או Dropbox.

### שלב 1 — לפתוח טרמינל

לוחצים על מקש Windows, כותבים `PowerShell`, ופותחים את "Windows PowerShell". החלון השחור/כחול שנפתח הוא הטרמינל. כל פקודה שכתובה כאן — מדביקים לשם ולוחצים Enter.

### שלב 2 — להתקין את uv

`uv` הוא הכלי שמתקין את כל השאר. מדביקים את השורה הזאת:

</div>

```powershell
powershell -c "irm https://astral.sh/uv/install.ps1 | iex"
```

<div dir="rtl">

כשזה מסתיים — **לסגור את חלון הטרמינל ולפתוח אותו מחדש.** בלי זה המחשב עוד לא יודע ש-`uv` קיים, וכל שאר השלבים ייכשלו.

### שלב 3 — להוריד את הפרויקט

</div>

```powershell
git clone https://github.com/zivbental/cernal_software.git C:\dev\cernal_software
```

<div dir="rtl">

אם המחשב עונה שהפקודה `git` לא מוכרת — צריך להתקין קודם Git for Windows מ-<https://git-scm.com/download/win>, ללחוץ Next על כל המסכים, לסגור את הטרמינל ולפתוח מחדש.

### שלב 4 — להיכנס לתיקייה

</div>

```powershell
cd C:\dev\cernal_software
```

<div dir="rtl">

זו הפקודה היחידה שתריצו כל יום לפני כל השאר. `cd` פירושו "לך לתיקייה".

### שלב 5 — להתקין את הסביבה

</div>

```powershell
uv sync --extra dev
```

<div dir="rtl">

הפקודה הזאת מתקינה את כל הספריות שהפרויקט צריך, כולל ViennaRNA.

חשוב להבין נקודה אחת: הפרויקט דורש **Python 3.13 בדיוק**, ובמחשבי Windows חדשים מותקן 3.14 — שהיא הגרסה הלא נכונה. `uv` פותר את זה לבד: הוא מוריד ומתקין 3.13 בשקט בתוך הפרויקט, בלי לגעת בפייתון שכבר יש לכם במחשב. **בגלל זה אסור להתקין עם `pip`** — אם תנסו, תקבלו שגיאה שלא ניתנת לפתרון.

### שלב 6 — לוודא שהכל עובד

</div>

```powershell
uv run pytest -q
```

<div dir="rtl">

זו סוללת הבדיקות של הפרויקט. אם ההתקנה תקינה, אחרי כדקה וחצי תראו בסוף שורה בסגנון:

</div>

```text

```

<div dir="rtl">

המספר יכול לגדול עם הזמן (אנחנו מוסיפים בדיקות). מה שחשוב הוא שכתוב **passed** ולא **failed**. אם זה מה שקיבלתם — סיימתם את ההתקנה, והמחשב שלכם מוכן.

כל מתודה ריקה בריפו כבר מכילה תיעוד שמסביר בדיוק מה היא אמורה להחזיר ולמה. זו המפרט — לא הצעה.

## 4. חוקי הזהב

שישה כללים. כל אחד מהם קיים כי בלעדיו משהו נשבר בשקט.

1. **אף פעם לא לדחוף ישירות ל-`main`.** רק עופר וזיו ממזגים. push ישיר ל-main שובר את הפרויקט לכל השאר בו-זמנית.
2. **לא כותבים פונקציה שכבר קיימת — שואלים את Claude Code לחפש קודם.** יש כבר `reverse_complement`, `gc_content`, `find_augs`, `hamming` ועוד ב-`src/engine/sequences.py`. עותק שני של פונקציה הוא עוד הזדמנות למספר שונה לאותו גודל.
3. **מריצים `uv run pytest -q` לפני כל push.** בדיקה אדומה שנדחפה לענף עוצרת את מי שמושך אותה אחריכם, ואת כל ה-PR.
4. **לא משנים קובץ משותף בלי להודיע בקבוצה.** `src/engine/sequences.py`, `src/engine/scoring/`, `src/engine/gates/tools/`, `src/engine/domain.py` — שינוי שם מזיז את המספרים של כל השאר בלי שאף אחד ישים לב.
5. **מדידה שנכשלה היא `None`, לעולם לא `0`.** זה החוק הכי חשוב כאן מדעית: המנרמל מתרגם `0.0` לציון **מושלם** במטריקות שבהן "נמוך יותר טוב", בעוד `None` מטופל נכון כ"חסר". `try: ... except: return 0.0` הופך כל תכנון שלא הצלחתם למדוד לתכנון שמנצח את כולם.
6. **אף פעם לא ממציאים שם מטריקה חדש.** קיימים בדיוק תשעה שמות מותרים, ב-`DEFAULT_V1` שבקובץ `src/engine/scoring/profiles.py`:

</div>

```text
state_separation
trigger_accessibility
gate_folding_energy
predicted_leakage
orthogonality
gc_content
dynamic_range
predicted_success_rate
circuit_complexity
```

<div dir="rtl">

כל שם אחר — `leakage`, `mfe`, `accessibility`, `switch_score` — נזרק בשקט, והמועמד מדורג כאילו המדידה חסרה, כלומר כגרוע ביותר. אם באמת חסרה מטריקה, זו החלטה של הצוות ושינוי מכוון ב-`profiles.py`, לא הוספה חד-צדדית.

**חוק נוסף שנובע מ-5 ומ-6:** הפונקציה `evaluate_design` מחזירה מספרים **גולמיים** בלבד. בלי נרמול, בלי משקולות, בלי "ציון סופי" משלכם. הנרמול והדירוג קורים במקום אחד, `src/engine/scoring/`, וזה בדיוק מה שמאפשר להשוות בין משפחות שערים שונות.

## 5. מה לעשות כשמשהו נשבר

### הבדיקות נכשלו — או שה-PR מסומן באדום

זה מצב תקין ולא סיבה לדאגה. ככה זה אמור לעבוד: הבדיקות תפסו משהו לפני שהוא הגיע לכולם.

1. להריץ `uv run pytest -q` אצלכם ולהעתיק את הודעת השגיאה **במלואה**.
2. להדביק אותה ל-Claude Code ולבקש: «הבדיקה הזאת נכשלת. תסביר לי למה, ותתקן בלי לשנות את הבדיקה עצמה.»
3. אם התיקון דורש לשנות בדיקה קיימת — **לעצור ולשאול בקבוצה.** בדיקה קיימת מתארת החלטה שכבר התקבלה; שינוי שלה הוא שינוי בהחלטה, לא תיקון.
4. לתקן, `git add -A`, `git commit -m "..."`, `git push`. ה-PR מתעדכן לבד.

### Git אומר "conflict"

קונפליקט פירושו ששניכם שיניתם את אותן שורות, ו-Git לא ממציא מי צודק. הוא לא מחק כלום.

</div>

```powershell
git checkout main
git pull
git checkout liran/trigger-scoring
git merge main
```

<div dir="rtl">

אם אחרי זה Git מדווח על קונפליקט — לפתוח את Claude Code ולומר: «יש לי merge conflict בקבצים האלה, תעזור לי לפתור אותו שורה-שורה ותסביר מה כל צד עשה.» בסוף מריצים את הבדיקות ודוחפים.

### שני דברים שאסור, אף פעם

- **אף פעם `git push --force`.** הפקודה הזאת מוחקת עבודה של אנשים אחרים מהשרת, ואי אפשר לשחזר אותה בקלות. אם מישהו — כולל Claude Code — מציע לכם להריץ אותה, זו הנקודה לעצור ולשאול.
- **אם Git אומר משהו שלא הבנתם — לא ללחוץ Enter על ניחוש.** לצלם מסך, להדביק בקבוצה, ולחכות דקה. אף פעם לא נשברה בעיה בגלל ששאלו; הן נשברו בגלל שניסו לתקן לבד עם פקודה שנראתה מבטיחה.

כלל אצבע: פקודות שקוראות מידע (`git status`, `git log`, `git diff`) בטוחות תמיד ואפשר להריץ אותן כמה שרוצים. פקודות שמכילות `--force`, `reset --hard` או `clean -fd` — לא להריץ לבד.

| פלט הקומפיילר ודוחות | זיו | `src/engine/stages/reporting.py` | `StructureRenderer`, `ReportBuilder` |
| שערי antisense ו-CRISPR | *ללא בעלים* | `src/engine/gates/antisense.py`, `src/engine/gates/crispr.py` | `AntisenseNotGate`, `CrisprGate` |

שימו לב לשורה של אביב: קוד ה"יצירה + ולידציה" שנכתב כקובץ אחד מתפצל כאן לשני קבצים בכוונה. יצירה שייכת למשפחת השער; כללי פסילה נוקשים שייכים לוולידטור, כדי ששלוש כימיות שונות לא יממשו את "אין קודון עצירה במסגרת" בשלוש דרכים שונות.
