This notebook is CERNAL's contest-ready, evidence-first record of meaningful software development. It complements the roadmap (future work), ADRs (decisions), tests, CI, and pull requests; it does not replace them.

## Scope and record rules

- **Current-record cutoff:** **2026-09-22**. The generated historical index below was built from `origin/main` at [`b8e20f5d6148`](https://github.com/zivbental/cernal_software/commit/b8e20f5d6148720a2de60e05d94b792eaacff71d) on that cutoff date.
- **Historical entries are generated evidence, not reconstructed narratives.** They preserve Git committer timestamps, author names, hashes, subjects, GitHub commit links, and changed-path evidence without inferring motivations, test outcomes, or approvals that the history does not prove.
- **Use a new team-written entry for every meaningful software change** (normally one coherent issue or PR). Record only work actually performed and verification actually run; link the underlying issue, PR, commit, CI run, test output, dataset, notebook, or decision record.
- Keep secrets, personal data, API keys, and unpublished sensitive biological data out of this public notebook. Link to approved restricted evidence instead when necessary.

## How to append a future entry

1. Copy the template below **above the generated historical index** and replace every placeholder before merge.
2. Use the work date in ISO form (`YYYY-MM-DD`); when timing matters, retain the commit's ISO-8601 timestamp and offset (for example, `2026-09-22T14:30:00+03:00`). Do not backdate an entry from memory—state uncertainty in **Problems / decisions**.
3. Cite immutable commit references as a short SHA linked to the full GitHub commit. For an implementation spanning multiple commits, list each SHA and identify the PR/issue that groups them.
4. State the exact commands, checks, reviewer, and outcome. “Not run” and “pending” are valid, auditable results; do not imply a test or approval occurred when it did not.
