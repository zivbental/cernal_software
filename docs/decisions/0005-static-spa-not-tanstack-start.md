# 0005 — Strip TanStack Start; ship a static SPA

**Status:** Accepted · 2026-08-25

## Context

The Lovable export arrived as a **TanStack Start** application: `@tanstack/react-start`
for SSR, `nitro` as the server runtime, `@cloudflare/vite-plugin` and `wrangler.jsonc`
targeting Cloudflare Workers, and `@lovable.dev/vite-tanstack-config` wrapping the Vite
plugin wiring. `src/server.ts` and `src/start.ts` were server entry points.

That is a second deployable unit with its own runtime, on infrastructure we do not use.
It also contradicts [ADR 0003](0003-same-origin-spa-session-auth.md), which is what lets
us authenticate with session cookies and no CORS.

## Decision

Keep TanStack **Router**; remove TanStack **Start**.

- Hand-written `vite.config.ts`: `@vitejs/plugin-react`, `@tailwindcss/vite`,
  `vite-tsconfig-paths`, `@tanstack/router-plugin` for file-based routes.
- `src/main.tsx` is a plain `createRoot` browser entry.
- Build output goes to `src/static/app/` with `base: "/static/app/"`.
- Django serves `index.html` from a catch-all (`apps/web/views.py`) so client-side routes
  survive a hard refresh or a shared link.
- Removed: `@tanstack/react-start`, `nitro`, `@cloudflare/vite-plugin`,
  `@lovable.dev/vite-tanstack-config`, `wrangler.jsonc`, `src/server.ts`, `src/start.ts`,
  and the Lovable SSR error-capture shims.

## Consequences

**Gained.** One deployment unit and one origin. Session cookies and CSRF work with no
configuration on either side. No Node process in production — the VPS serves static files
through Whitenoise, so Node is a build-time dependency only. Six fewer dependencies, and
a Vite config a student can read.

**Given up.** No server-side rendering: no SEO for the app shell, and a blank frame until
the JS loads. Neither matters for an authenticated internal tool. No streaming or server
functions — every server capability comes from the Django API instead, which is where we
want it.

**Notes.** `routeTree.gen.ts` is generated by the router plugin and gitignored. During
development, Vite on :5173 proxies `/api`, `/media` and `/admin` to Django on :8000, so
the browser still sees a single origin and cookies behave exactly as in production.

**Revisit when** the app needs public, indexable pages — most likely the iGEM wiki
content, which is a separate site anyway.
